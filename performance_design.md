# Производительность — домашнее задание 05

Вариант 9: электронная почта. Пользователи, папки и письма хранятся в MongoDB.
Кеш и счётчик запросов реализованы обычными словарями Python в `performance.py`.
Они работают в памяти одного процесса API. Redis и другие новые сервисы не нужны.

## 1. Частые операции и требования

| Операция | Когда выполняется | Что может занимать время |
| --- | --- | --- |
| `GET /api/v1/folders` | Открытие почты, обновление списка папок | Выборка и сортировка папок в MongoDB |
| `GET /api/v1/folders/{folder_id}/messages` | Открытие папки, повторное обновление списка писем | Проверка владельца, выборка и сортировка писем, подготовка JSON |
| `GET /api/v1/messages/{code}` | Открытие одного письма | Поиск письма по индексу, проверка владельца |
| `GET /api/v1/users` | Поиск пользователя по маске | Регулярное выражение может просматривать много документов |
| `POST /api/v1/auth/login` | Вход пользователя | Поиск пользователя и проверка хеша Argon2id |
| Создание пользователя, папки или письма | Добавление данных | Хеширование пароля, запись и обновление индексов MongoDB |

Два первых чтения — hot paths: пользователь может повторять их значительно
чаще, чем создавать папки или письма. Внешние API приложение не вызывает.
Сложных вычислений для чтения почты нет. Argon2id — намеренно затратная операция;
результаты проверки пароля и сессионные токены в кеш ответов не помещаются.

Учебные цели для локального Docker-запуска, одного процесса API и небольших
списков, до 100 объектов в ответе:

| Метрика | Цель |
| --- | --- |
| p95 времени чтения из кеша | Не более 100 мс |
| p95 чтения из БД | Не более 200 мс |
| p95 создания папки или письма | Не более 300 мс |
| p95 регистрации и входа | Не более 500 мс |
| Пропускная способность чтения | Не менее 20 запросов в секунду при повторном чтении |

p95 — время, в которое укладываются 95% запросов. Это выбранные требования,
а не гарантии для любой машины или доказанный результат нагрузочного теста.
Большие письма и списки увеличивают стоимость сериализации и передачи ответа.

## 2. Стратегия кеширования

| Endpoint | Что хранится | Ключ | Стратегия | TTL | Когда сбрасывается |
| --- | --- | --- | --- | --- | --- |
| `GET /api/v1/folders` | Публичные данные папок, в том числе пустой список | `user_id` | Cache-Aside | 30 секунд | После успешного создания папки этого пользователя |
| `GET /api/v1/folders/{folder_id}/messages` | Публичные данные писем, в том числе пустой список | `(user_id, folder_id)` | Cache-Aside | 15 секунд | После успешного создания письма в этой папке |

Список папок меняется сравнительно редко. Письма появляются чаще, поэтому их
TTL короче. Хранятся готовые DTO ответа, без хешей паролей и токенов.
Данные разных владельцев имеют разные ключи.

Выбрана Cache-Aside: API сам проверяет кеш, а при промахе читает MongoDB.
Отдельного компонента для Read-Through нет. Write-Through потребовал бы
пересобирать весь список при каждой записи. Write-Back откладывает запись в БД
и усложняет сохранность данных; здесь запись всегда сначала выполняется в MongoDB.

Поиск пользователей по произвольным маскам пока не кешируется: вариантов ключа
много, а создание пользователя потребовало бы сбрасывать результаты разных масок.
Для получения одного письма уже есть индекс `_id`. Оптимизация двух списков
покрывает обязательные два endpoints и остаётся простой.

## 3. Как работает кеш и инвалидация

1. Middleware проверяет токен до выполнения закрытого endpoint.
2. При чтении писем API проверяет существование папки и владельца в MongoDB.
   Эта проверка выполняется даже при попадании в кеш.
3. `TTLCache.get_or_load()` удаляет истёкшие записи и ищет ключ.
4. Если запись есть, API возвращает её и заголовок `X-Cache: HIT`.
5. Если записи нет, API выполняет выборку списка в MongoDB. Успешный результат
   сохраняется до `monotonic() + TTL`, а ответ содержит `X-Cache: MISS`.
6. Создание папки сначала записывает её в БД, затем удаляет кеш списка папок
   владельца. Создание письма аналогично удаляет кеш списка писем этой папки.
   Следующее чтение получает актуальный список и снова заполняет кеш.

Ошибки и ответы `404` в кеш не записываются. Неудачная операция создания не
сбрасывает кеш, поскольку данные не изменились. Пустой список кешируется:
отсутствие писем тоже является успешным результатом чтения.

TTL считается через монотонные часы: изменение системной даты не продлевает
жизнь записи. Время начинается после завершения загрузки. Каждому из двух кешей
разрешено хранить до 1000 записей; при заполнении удаляется самая старая по
времени добавления. Истёкшие записи удаляются при следующем чтении этого кеша,
фонового потока нет.

У каждого кеша свой `Lock`. Он защищает проверку, загрузку и инвалидацию от
одновременного выполнения в потоках FastAPI. Если чтение началось перед записью,
операция создания дождётся окончания загрузки и удалит полученный результат.
После успешного ответа на создание старый список уже не останется в кеше.
Во время загрузки одного промаха другие операции с этим же кешем ждут lock:
это ограничение простой учебной реализации.

В API нет изменения и удаления сущностей, поэтому новые HTTP-методы не добавлены.
Создание меняет кешируемые списки и выполняет требуемую инвалидацию при изменении
данных. При изменении документов напрямую через `mongosh` API не получает
уведомления: список обновится по TTL. Если папка удалена или сменился её владелец,
проверка доступа к письмам сразу отклонит запрос прежнего владельца, даже если
список писем ещё находится в кеше.

## 4. Выбор rate limiting

Ограничивается `POST /api/v1/auth/login`: повторные попытки могут создавать
нагрузку на MongoDB и дорогостоящую проверку Argon2id. Для этого endpoint выбран
Fixed Window Counter, 10 попыток в минуту с одного IP. Остальные endpoints
сохраняют прежнее поведение. Ролей обычного и премиум-пользователя в варианте нет.

Алгоритм проще Token Bucket и Sliding Window: для IP достаточно номера окна
и счётчика. Leaking Bucket потребовал бы очереди и ожидания обработки, что
не нужно для входа. Ограничение фиксированного окна допускает всплеск на его
границе: например, 10 запросов перед началом новой минуты и ещё 10 сразу после.
Для учебной работы этот недостаток принимается.

## 5. Как работает ограничение запросов

1. Middleware берёт IP из `request.client.host` до чтения тела запроса,
   обращения к БД и проверки пароля.
2. Номер окна равен `floor(Unix time / 60)`. Окна привязаны к минутам UTC,
   например от `19:00:00` до `19:00:59` UTC.
3. Записи прошлых окон удаляются. Если у IP ещё нет счётчика, он начинается с 0.
4. Пока счётчик меньше 10, он увеличивается, запрос проходит в endpoint.
5. Когда 10 попыток уже использованы, middleware сразу возвращает `429`.
   MongoDB и Argon2id для такого запроса не вызываются.
6. На границе следующего окна для IP снова доступны 10 попыток.

Успешный вход, неверный пароль, неизвестный логин и неправильный JSON расходуют
попытку. Блокированные запросы не увеличивают счётчик сверх 10. `Lock` защищает
его проверку и увеличение: параллельные запросы не получают лишних попыток.

Ответы `200`, `400`, `401` и `429` этого endpoint содержат:

| Заголовок | Значение |
| --- | --- |
| `X-RateLimit-Limit` | `10` — число попыток в одном окне |
| `X-RateLimit-Remaining` | Число оставшихся попыток после текущего запроса |
| `X-RateLimit-Reset` | Unix timestamp начала следующего окна, в секундах |

При превышении лимита тело ответа:

```json
{"detail":"Too many login attempts"}
```

IP используется вместо логина, потому что до входа нет подтверждённого
пользователя. Несколько людей с общим внешним IP делят лимит. За прокси адрес
клиента зависит от настройки сервера; локальные примеры рассчитаны на прямое
подключение. Смена IP и границы окон ограничивают применимость этой простой схемы.

## 6. Эффект и измерение

При попадании в кеш папок выборка списка в MongoDB не выполняется. Для N чтений
одного списка за TTL без изменений нужна одна выборка вместо N. Например,
для 10 чтений это 1 вместо 10. Сериализация и передача JSON остаются.

Для писем проверка владельца сохраняется. Без кеша на каждое чтение приходятся
проверка папки и выборка писем. Для 10 повторных чтений получается 10 проверок
и 1 выборка, то есть 11 обращений вместо 20. Кеш помогает особенно тогда,
когда выборка писем существенно дороже проверки одной папки по индексу.

Rate limiting ограничивает количество попыток входа, доходящих до БД и проверки
хеша. Из 15 запросов одного IP в одном окне проходят максимум 10, остальные 5
получают `429`. Он защищает доступные ресурсы от повторяющихся запросов одного
клиента, но сам по себе не ускоряет отдельную разрешённую попытку входа.

| Метрика | Как измерять |
| --- | --- |
| Время ответа: среднее, p50, p95 | Замерять от отправки HTTP-запроса до получения всего ответа; разделять HIT и MISS |
| Пропускная способность | Число завершённых запросов / продолжительность серии в секундах |
| Cache hit rate | Число ответов с `X-Cache: HIT` / число ответов с `X-Cache: HIT` или `MISS` |
| Количество и время запросов MongoDB | Профайлер MongoDB при отдельном измерении либо счётчик вызовов драйвера в тестах |
| Доля блокировок входа | Число ответов `429` / число попыток входа |
| Ошибки | Количество ответов `400`, `401`, `404`, `409`, `429`, `5xx` отдельно |
| Память и CPU | `docker stats`, размеры ответов и число активных ключей кеша |

Hit rate умножают на 100%, чтобы получить процент. Например, одна загрузка
и девять попаданий дают 90%. Ответы ошибок не входят в знаменатель.
Высокий hit rate полезен вместе с уменьшением обращений к БД и времени ответа:
одного процента попаданий недостаточно для оценки всей системы.

### Повторяемая проверка hit rate

После получения токена выполнить следующий Python-код за время меньше TTL.
Вместо `PASTE_ACCESS_TOKEN_HERE` нужно вставить свой токен. Для проверки писем
заменить URL на `/api/v1/folders/<folder_id>/messages` своей папки.

```python
from time import perf_counter
from urllib.request import Request, urlopen

token = "PASTE_ACCESS_TOKEN_HERE"
url = "http://localhost:8000/api/v1/folders"
hits = misses = 0
elapsed = []
for _ in range(10):
    started = perf_counter()
    with urlopen(Request(url, headers={"Authorization": "Bearer " + token})) as response:
        response.read()
        status = response.headers["X-Cache"]
    elapsed.append((perf_counter() - started) * 1000)
    hits += status == "HIT"
    misses += status == "MISS"
print("HIT:", hits, "MISS:", misses)
print("Hit rate:", 100 * hits / (hits + misses), "%")
print("Mean response:", sum(elapsed) / len(elapsed), "ms")
```

Если до серии ключ отсутствовал, ожидаются один MISS и девять HIT. Если список
уже читали недавно, все десять ответов могут быть HIT. Для сравнения выполнить
серии после истечения TTL и сразу после заполнения; держать одинаковыми данные,
число запросов и условия запуска. Для проверки цели 20 запросов/с нужна отдельная
серия с такой частотой, затем следует посчитать p95 и долю ошибок. Короткая
последовательность из десяти запросов проверяет механизм, а не предел нагрузки.

### Автоматические проверки

Тесты считают реальные вызовы `Collection.find`: повторное чтение списков не
выполняет вторую выборку папок или писем. Проверяются TTL без ожидания через
подмену часов, сброс кеша после создания, кеширование пустых списков, разделение
владельцев и обязательная проверка доступа даже при заполненном кеше.
Для лимита проверяются заголовки, все типы попыток, `429` до обращения к БД,
новое окно, отдельные IP и 40 параллельных обращений: проходят только 10.
Сохраняются проверки остальных операций API и валидации MongoDB.

### Проверка в Docker

12 октября 2026 года выполнена проверка API через HTTP с настоящей MongoDB 7:
по 30 последовательных чтений списка из одной папки с одним письмом. Перед
каждой серией кеш был сброшен операцией создания.

| Список | MISS | HIT | Hit rate | Первый MISS, мс | p95 ответов HIT, мс |
| --- | ---: | ---: | ---: | ---: | ---: |
| Папки | 1 | 29 | 96,7% | 2,499 | 1,950 |
| Письма | 1 | 29 | 96,7% | 2,986 | 2,138 |

Это короткая функциональная проверка на небольшой выборке в облачной среде,
без параллельной нагрузки. Первый MISS — один запрос, поэтому сравнение его
времени с p95 HIT не доказывает величину ускорения. Уменьшение выборок MongoDB
подтверждается отдельными тестами со счётчиком вызовов драйвера.

В контейнере также проверены инвалидация обоих списков после создания,
ответ `429` после десяти попыток входа и обязательные заголовки.
После перезапуска API кеши, лимит и сессии очистились, а папка и письмо сохранились
в MongoDB и снова читались с MISS после повторного входа. Все 37 тестов прошли.

## Ограничения запуска

Нужен один процесс Uvicorn: сессии, кеши и лимиты не разделяются между workers
и контейнерами. Перезапуск очищает их, включая счётчики попыток, но сохраняет
данные MongoDB. Кеш ограничен числом записей, а не размером в байтах: очень
большие списки всё равно могут потребовать много памяти. Фиксированное окно
использует системное UTC-время, поэтому его счётчики зависят от настройки часов.
Эти ограничения соответствуют простому локальному учебному решению.
